# 阶段复盘

## 阶段目标

从可演示的 Streamlit 原型迁移到能够支撑正式产品演进的 Trident 基座，同时保留既有研究能力，并形成海外与中国大陆双区域部署思路。

## 已取得成果

- 验证了“研究能力不等于 Prompt 能力”的产品定位，明确以问题定义、任务拆解、证据校验和商业判断为核心。
- 保留 Python 研究内核，建立 FastAPI 与 Next.js 的企业化迁移路径。
- 把通用行业研究、企业战略研究、构建式和审阅式路径统一到同一领域模型。
- 明确长期记忆、持续感知、动态 Scorecard、Adaptive Action Plan 和多场景模块的方向。
- 建立独立 Trident 仓库和 CloudBase Demo 部署基线。

## 主要问题

1. 原型页面承担了过多业务状态，UI 重跑容易产生断裂或重复执行。
2. 模型结构化输出不稳定时，严格校验会使流程停在某个 Gate。
3. 同步执行搜索与报告生成容易触发托管平台超时。
4. SQLite 适合演示，但无法自然满足多用户、备份和容器重建后的持久化。
5. 过早叠加功能导致核心四路径缺少稳定的端到端回归。

## 根因

- 领域状态、页面状态和任务状态没有在原型阶段完全分离。
- AI 输出协议缺少版本化、修复器和降级策略。
- 部署平台约束在开发后期才纳入长任务设计。
- 研究方法、产品规则和工程合同此前散落在代码及对话中。

## 关键经验

- 人工审核应处理判断责任，而不应成为无法继续的技术阻塞点。
- “不允许空白”不等于可以编造；应通过扩大检索、区间估算、明确假设和置信度形成可用输出。
- 报告展示与内部证据追踪必须分层：正文专业连贯，审阅工作台保留完整来源和限制。
- 先稳定领域合同和端到端路径，再增加场景包与复杂算法。
- Demo 的低成本方案必须被明确标记，不能静默成为生产架构。

## 后续行动

- 以四条主路径作为每次发布的最小回归集。
- 建立异步 Job 状态机、幂等步骤和断点恢复。
- 为模型输出增加 Schema 版本、自动修复、重试和人工接管。
- 将项目、证据、分析、报告、评分、行动与记忆拆成规范化数据模型。
- 建立产品决策、工程决策和研究标准的同步更新机制。

## 下一阶段成功标准

- 任一研究任务失败后可以从失败步骤恢复，不重复已完成搜索。
- 任一路径切换不会丢失项目内容或人工修改。
- 企业 Scorecard 和 Action Plan 在信息充分时稳定生成，在信息不完整时给出可解释估算而非空白。
- Demo 数据可持久保存；正式环境只使用 PostgreSQL。
- 核心指标包括成功率、平均生成时长、人工修改次数、证据采用率和单项目成本。
