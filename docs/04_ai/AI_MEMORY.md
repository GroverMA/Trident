# Trident AI 长期记忆

本文件供后续 AI 编码助手、研发人员和研究产品负责人快速恢复项目上下文。它记录长期稳定事实与不可轻易破坏的约束，不替代代码、测试或架构决策记录。

## 1. 项目身份

- 产品名：**Trident**。
- Slogan：**Dive Deep into Industries. Surface with Direction.**
- 定位：企业行业研究与战略决策智能体。
- 原始 Industry Analyst 是历史产品和回归参照；除非用户明确要求，禁止修改其仓库。
- Trident 是独立升级仓库，当前需要兼顾融资 Demo、未来 SaaS 和企业私有化部署。

## 2. 产品真相

- Trident 的护城河是问题定义、研究拆解、证据纪律、反证、商业判断和行动闭环，不是单纯调用模型或生成文档。
- 构建式研究与审阅式研究是同一项目的两种工作路径，不是用户权限身份。
- 通用行业研究与企业战略研究共享行业研究底座；企业研究额外使用企业一手信息、战略意图、Scorecard 和 Action Plan。
- 企业一手资料是增强项：通用报告无需上传；企业定制判断必须有战略意图和经审核的一手资料。
- 未来优先场景包括 PE/VC 决策和中小企业增长决策。

## 3. 不可破坏的研究规则

1. 先理解用户 Prompt，再动态组织报告；SOP 提供方法和默认逻辑，不是僵硬目录。
2. 通用底座通常覆盖行业定义、赛道与产业链、市场规模、竞争格局、驱动因素和 Future Outlook。
3. 事实、来源观点、分析推断和建议必须在内部结构中区分。
4. 核心结论应有来源、适用边界、时间和地域口径；预测应有假设、触发条件和反证条件。
5. 报告中不得暴露 Evidence ID、Finding ID、Prompt、内部 Schema、错误信息或“资料不足”等系统措辞。
6. 核心章节不能空白；信息不足时应继续检索、进行区间估算或采用明确假设，并在审阅层表达置信度，禁止编造精确事实。
7. 报告正文使用独立第三方、专业、连贯的行业研究语言；引用集中到来源系统或附录。
8. 任何特定研究机构名称不得作为系统方法论品牌出现在产品、流程或报告中。

## 4. Scorecard 与 Action Plan

- Scorecard 维度由行业趋势、企业战略意图和企业现状动态决定，不应永远固定六维。
- 每个维度需要：指标定义、公司得分、市场平均基准、战略目标要求分、差距、权重、证据和置信度。
- 市场基准是同类玩家的实际平均能力，不是理想状态，不能机械设为 90 分。
- 雷达图同时显示公司、市场平均和战略目标三条线；表格保留计算解释。
- Action Plan 由“公司相对市场差距 + 公司相对战略目标差距 + 企业约束”推导。
- Action Plan 只需区分短期与长期，不强制生造固定时间段。
- 每项行动回答：做什么、谁负责、何时开始、如何衡量、依赖与风险。

## 5. 工程原则

- Python 保留为研究与 AI 内核；FastAPI 是服务边界；Next.js 是正式工作台。
- Streamlit 仅保留历史演示与对照，不作为 Trident 新架构的主承载。
- 正式数据库为 PostgreSQL；SQLite 只在显式 Demo 模式使用，禁止生产环境静默回退。
- 长任务必须演进为异步 Job/Worker，支持幂等、重试、恢复、取消和进度事件。
- 场景、行业、Skill、模型和算法通过稳定合同扩展，避免在主流程堆叠条件分支。
- 同一代码库支持不同区域部署，配置差异不得演化为两套业务代码。
- Vercel 海外版与腾讯云大陆版必须共享同一研究流程、功能、领域/API/数据契约、Skill、
  Prompt、报告规则和发布版本。今后所有迁移、新功能和修复默认同时作用于两个区域。
- 仅部署拓扑、域名、云资源、Secret、Provider Endpoint、数据驻留和合规配置可以按区域
  不同；通过环境配置或适配器实现，禁止复制或条件分叉领域研究逻辑。
- 任一区域未完成构建和受影响流程验收时，不得把变更标记为双区域发布完成。

## 6. 首选技术栈

| 层 | 当前/首选技术 | 长期方向 |
|---|---|---|
| Web | Next.js、React、TypeScript | 企业门户或插件集成 |
| API | Python、FastAPI、Pydantic | 企业 API 网关 |
| 任务 | 单 Worker 起步 | Celery/Temporal 类高可用调度 |
| 数据 | SQLite Demo、PostgreSQL 正式环境 | 多租户、企业私有库、知识图谱 |
| 对象存储 | 平台对象存储 | 企业文档与版本治理 |
| AI | 可替换模型 Provider、Skill Registry | 模型路由、评估与专业算法 |
| 检索 | 搜索与抓取工具 | 持续感知、内外部联合检索 |
| 部署 | 海外托管云、CloudBase Demo | SaaS、VPC、Kubernetes |

## 7. 命名与代码约定

- 新分支默认使用 `codex/` 前缀。
- API 使用 `/v1` 版本前缀；领域状态必须使用受控枚举。
- 前端不直接持有服务端密钥；日志不得输出完整 Prompt、文件内容或凭证。
- Pydantic 模型、数据库迁移、前端类型和测试需要同步更新。
- 文件修改优先使用小范围、可审阅补丁；保留用户未关联的工作区改动。
- 不使用破坏性 Git 操作，不重写用户历史。

## 8. UI 约定

- 视觉风格：简洁、白色与透明感为主，青绿色作为专业强调色。
- 青绿色主按钮必须使用高对比度白色文字。
- 研究流程应在一个主工作台中连续呈现，避免依赖侧栏寻找下一步。
- 已完成节点允许回看和按规则重新运行；回退应清楚说明哪些下游工件会失效。
- 历史项目需显示状态、进度与当前节点，并支持继续、存档和删除。
- 两种研究路径具有相同视觉权重，可随时切换且不丢失内容。

## 9. 报告约定

- 标题层级必须连续，例如 1、1.1、1.1.1，不能跨章节跳号。
- 段落按完整逻辑换行，禁止一个句子中途断段，也禁止整页不分段。
- 中文标点不得出现在新段落开头；清理异常空格和 Markdown 残留符号。
- 网页、Word 与 PDF 使用同一内容 AST 和样式设置来源。
- 支持动态标题，重点和篇幅应呼应用户最关心的问题。
- 市场规模部分应展示口径、公式、参数、交叉验证和敏感性，而非只给结果。

## 10. 安全与数据边界

- 绝不把 API Key、数据库连接串、客户文件或内部资料写入仓库。
- 如果密钥曾出现在截图、对话或日志中，视为可能泄露并建议轮换，不从历史材料中恢复明文。
- Demo 环境提示用户只上传脱敏/模拟资料；机密资料必须进入有明确权限、存储和保留策略的企业环境。
- 企业资料需要接受、拒绝和删除三种操作；拒绝资料不阻塞已满足条件的项目。
- 公开 GitHub 仓库不等于自动授予使用许可；正式商业合作前应补充许可证和知识产权声明。

## 11. 常见陷阱

- 把页面控件状态当成项目真实状态，导致刷新后流程错乱。
- 每次补检都重新执行全部研究，造成耗时和重复成本。
- 模型少一个枚举或字段就让整个流程永久卡住。
- 把市场平均误写成战略目标或行业最优水平。
- 审阅单个模块时重新生成整份报告并丢失未选模块。
- 使用同步请求执行长搜索和完整报告生成。
- 容器中使用 SQLite 但没有持久卷，却向用户承诺长期记忆。

## 12. 永远不要做

- 不得修改原 Industry Analyst 仓库来完成 Trident 升级。
- 不得硬编码或提交任何密钥。
- 不得用虚假引用、虚构数据或不存在的企业事实填补报告。
- 不得让失败的模型输出覆盖已经通过人工审核的工件。
- 不得在生产环境自动降级到 SQLite。
- 不得因路径切换而清空证据、报告版本或人工修改。
- 不得把内部研究编码写入面向客户的报告。
- 不得创建长期分叉的大陆版/海外版研究流程、功能实现或 Skill；不得只更新一个区域后
  宣称功能完成。

## 14. 长期能力地图

- Profile Engine：主动访谈形成企业或投资标的画像，并理解管理者决策风格。
- Benchmark & Case Library：沉淀行业、公司、项目、判断和结果案例。
- Simulation Engine：模拟市场、客户、竞争者和投资委员会判断。
- Benchmark Engine：建立 Company Scorecard 与目标差距。
- Adaptive Planning Engine：根据执行反馈动态调整行动计划。
- Memory Layer：保存企业、项目、对话、假设、决策和行动的时间化历史。
- Enterprise Sensing Engine：持续抓取行业、政策、竞争者、客户和经营信号。
- Multi-role Workspace：为管理层、研究负责人、投资经理和执行责任人提供不同视图。

## 15. 与用户协作

- 写代码前解释目的、达到的结果、采用的工具和需要的用户输入。
- 重要产品判断分阶段让用户审阅；已授权的实现任务应主动完成并验证。
- 先报告结果和证据，再说明技术细节。
- 如果需要新的付费服务、外部权限或会改变产品方向，应明确提出，不自行扩大范围。
