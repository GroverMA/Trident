# Business Rules

## 0. Dual-region Product Parity Rules

1. Vercel 海外版与腾讯云大陆版是同一产品的两个区域部署，不是两个版本或两条产品线。
2. 两个区域必须使用同一套研究流程、功能集合、业务规则、领域模型、API 契约、Skill
   版本和报告标准。
3. 所有研究流程迁移、新功能、缺陷修复、Schema 变更和 Skill 更新必须同时适用于两个
   部署目标；禁止只在某一区域维护业务代码。
4. 允许差异仅限部署拓扑、云资源、域名、密钥、模型/搜索 Provider 配置、数据库实例、
   对象存储、数据驻留和区域合规要求，并通过环境配置或稳定适配器表达。
5. 若区域供应商暂不支持某项基础设施能力，必须记录为部署限制并提供等价适配或明确
   临时降级；不得静默改变研究方法、输出内容或用户功能。
6. 一个版本只有在海外与大陆均完成构建、健康检查和相关核心流程验收后，才可标记为
   双区域发布完成。

## 1. Research Path Rules

1. 构建式与审阅式是研究方式，不是用户权限或身份。
2. 两种方式共享同一个 `project_id`、证据库、分析产物、报告版本和企业资料。
3. 切换研究方式不得重置任何已保存内容。
4. 项目可返回已完成节点修改；下游产物必须标记“可能失效”，由用户选择重新运行，而不是静默覆盖。

## 2. Project Status Rules

建议状态：

`draft → planning → researching → evidence_review → analyzing → reporting → review → completed`

附加状态：`paused`、`archived`、`terminated`、`failed_recoverable`。

- 存档：保留全部数据，只从默认进行中列表移出。
- 终止：停止未来任务，保留历史和报告。
- 删除：需要二次确认；生产环境采用软删除和保留期。
- 恢复项目：进入最近未完成或最近活动节点。

## 3. Input Validation Rules

- 通用研究必须提供行业、地区、核心研究目标。
- 企业战略路径必须额外提供目标企业和企业战略意图。
- “需要支持的业务决策”不作为企业路径的重复必填项。
- 时间范围、计量口径、产品范围和地区边界不清时，Gate 0 生成待验证问题。
- 用户确认口径前不得正式执行下游研究；审阅式可后台预备，但不可宣称范围已确认。

## 4. Market Definition Rules

- 市场定义包含纳入、排除、相邻领域、地理、时间与计量口径。
- 待验证问题必须有对应的研究者回答字段，且问题和回答均可编辑。
- 用户修改口径后，所有引用旧口径的任务标记为需复核。

## 5. Evidence Rules

- Evidence 必须保留来源 URL/文件、标题、日期、原文摘要和适用范围。
- 区分 `fact`、`data`、`source_viewpoint`、`analyst_inference`、`forecast`。
- 同一来源的多个摘录不得被误当作多个独立来源。
- 证据评分是辅助信息，不以不透明的 A/B/C 等级作为唯一展示。
- 推荐证据同时考虑质量、Prompt 相关性和覆盖增量。
- 构建式 Gate 1 的确认框为必选；未确认不得进入行业分析。
- 未覆盖问题不会触发无限补检；用户可接受分析师处理方式或补充自己的判断。

## 6. Enterprise Data Rules

- 企业资料默认私有，不能出现在公开案例或日志。
- 每批资料记录数据层面、期间、来源角色、战略关系和敏感级别。
- 只有 `accepted` 的资料可进入企业分析。
- `rejected` 资料不进入上下文；`deleted` 资料从当前项目移除并记录审计事件。
- 改变审核状态后必须使相关缓存和下游产物失效。
- 上传成功后清空输入控件，但已加入清单仍可见。
- 文件大小产品目标为单文件 300 MB；平台限制不足时应前置提示而非上传后失败。

## 7. Analysis Rules

- 通用分析至少覆盖：行业定义、赛道与产业链、市场规模、竞争格局、驱动因素和 Future Outlook。
- 模块标题与重点根据 Prompt 动态调整，但逻辑顺序应连贯。
- 模型返回同义字段、`null` 或未知枚举时先归一化，再校验。
- 竞争格局和驱动因素不得留空；若一次生成失败，重试当前模块或使用已接受证据生成保守结构化判断。
- 分析师推断必须能解释依据和反证条件，但正式报告无需暴露内部字段。

## 8. Forecast Rules

- 优先使用可验证的历史序列和驱动变量；数据不足时采用因果情景法。
- 所有预测给出基准/加速/受阻情景、触发条件和可观测指标。
- 定量模型不得仅因“机器学习”标签而使用；必须说明样本、特征、验证和误差。
- 不得把来源观点直接当作 Trident 的确定预测。

## 9. Scorecard Rules

- 维度从行业关键成功因素、未来趋势和企业战略意图共同生成。
- 公司分、市场基准和战略目标要求是三个不同概念。
- 市场基准为可比玩家平均水平，不固定为 90 分；目标要求由战略意图决定。
- 每个分数必须绑定量化指标或可解释代理指标、依据和置信度。
- 即使资料有限也生成估计值，明确置信度；不得显示 `None`、空白或“资料不足”。
- 雷达图至少需要三个有效维度。

## 10. Action Plan Rules

- 行动必须对应一个或多个 Scorecard 差距和外部趋势。
- 只分短期与长期。
- 每项写明做什么、谁负责、何时开始、如何衡量、依赖和风险。
- 优先级、替代选项与组合风险使用 bullet points。
- 企业战略意图改变时，Action Plan 必须重新评估。

## 11. Revision Rules

- 审阅者选择一个模块时，只修改该模块。
- 未选择模块使用上一稳定版本，不重新送入生成模型。
- Scorecard 与 Action Plan 只有在被选中，或其明确依赖模块发生实质变化且用户同意时才更新。
- 每轮保留问题、AI 建议、用户决定、差异和版本号。
- 生成失败不得覆盖上一稳定版本。

## 12. Report Rules

- 正式报告是专业文章，不是对 Prompt 的逐题回答。
- 不得出现 `EVD-`、`FND-`、结构化字段名、模型报错、Emoji 或内部 SOP 品牌来源。
- 不得在正式报告写“资料不足”“本模块仅能覆盖”“建议补充某来源”等工作底稿语言。
- 证据局限放在审阅工作台“报告注意点”，不进入正式正文。
- 标题分级连续；正文完成一个逻辑段落后换行，不做随机断行。
- 标点不得作为新段落首字符。
- 网页、Word 和 PDF 使用同一内容与样式配置。

## 13. Audit Rules

以下动作需要审计：项目创建/删除、范围确认、证据与企业资料审核、模型生成、人工编辑、模块修订、报告发布、权限变更和导出。

审计事件至少包含：主体、动作、对象、项目/租户、时间、前后版本、结果和相关任务 ID；不得记录密钥或完整机密正文。
